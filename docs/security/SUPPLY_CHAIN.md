# Supply-chain security

Implements NFR-SEC-13 (Phase 13, ADR-0030). Everything here is executable: `python
scripts/security_gate.py --strict` runs it and returns a machine-readable verdict Phase 14 CI
invokes as-is. Phase 13 wires **no** CI workflow.

## 1. Dependency strategy

**Compatibility ranges in `pyproject.toml`; exact, hash-pinned resolution in committed locks.**
Ranges keep the project installable next to other software; the lock makes an installation
reproducible and lets a scanner name the exact versions in use. Every direct runtime dependency has
an upper bound (a test refuses one that does not).

| File | Contents | Generated by |
|---|---|---|
| `requirements/runtime.lock` | runtime closure, universal (all platforms), `sha256` for every file | `uv pip compile pyproject.toml --universal --python-version 3.11 --generate-hashes` |
| `requirements/dev.lock` | runtime plus the `dev` extra | same, `--extra dev` |
| `requirements/security-tools.lock` | `pip-audit` and its closure, **kept out of runtime** | same, from `requirements/security-tools.in` |
| `frontend/package-lock.json` | the dashboard's npm closure, lockfile v3, every package with an `integrity` digest | `npm install --package-lock-only` |

Install reproducibly with `uv pip install --require-hashes -r requirements/runtime.lock`.

**Update policy.** Re-run the `uv pip compile` commands above deliberately (never as a side effect of
installing), read the diff, run `security_gate.py`, then commit lock and `pyproject.toml` together.
The checker fails if the lock and `pyproject.toml` disagree.

**Vulnerability review.** `pip-audit -r requirements/runtime.lock --require-hashes` and `npm audit
--omit=dev --audit-level=high` run in the gate. They report only what their advisory databases know:
a clean run is not a claim that no vulnerability exists. A finding is fixed by updating the lock, or
recorded with a reasoned, time-boxed exception; none is suppressed silently.

## 2. Prerelease policy

Phase 14's `requirements/build-tools.lock` pins the editable-install build backend separately from
runtime and development dependencies. CI installs it with `--require-hashes --no-deps`; these tools
are not copied into the backend final image. The existing clean-install validator separately checks
the declared metadata in an empty environment, so it intentionally does not replace lock validation.

A prerelease may be locked only if `configs/security/supply-chain-policy.toml` names it with a
reason, and an entry that matches no locked prerelease is itself an error (exceptions do not go
stale). Current exceptions (both verified against the package index in Phase 13):

- `opentelemetry-exporter-prometheus`: PyPI publishes it *only* as `0.xxb0` betas; there is no stable
  release. It is the bridge behind `/metrics`; replacing it means writing our own, a larger risk than
  pinning a beta. `pyproject.toml` caps it below 1.0 and the lock pins it exactly, in step with the
  `opentelemetry-sdk` release train.
- `opentelemetry-semantic-conventions`: a transitive dependency of the SDK versioned in lockstep
  with the exporter.

Everything else is stable.

## 3. Lock integrity checks (`scripts/check_dependency_lock.py`)

Every requirement is an exact `name==version` with at least one `sha256`; no requirement resolves
from a URL or VCS and no `--index-url`, `--extra-index-url` or `--find-links` appears (a
dependency-confusion vector); every direct dependency is locked at a version its range accepts; the
dev lock contains every runtime package at the exact same resolved version (extra dev-only packages
are allowed); the frontend lockfile is v3, every package has an integrity
digest, none resolves outside the npm registry, and production dependencies are exact versions.
`tests/security/test_security_gate.py` feeds it deliberately broken locks so it cannot pass vacuously.

Found and fixed in Phase 13: 26 of 34 packages in the frontend lockfile had no `integrity` digest
(the lock had been generated from a local cache), so an installer could not verify those tarballs.
It was regenerated from the registry; only two patch versions moved.

## 4. Static analysis (SAST)

`ruff check --select S --ignore S101 src` (flake8-bandit rules). **No second scanner was added**:
ruff is already the project linter, and its `S` rules cover the classes that matter here (unsafe
subprocess and shell, `eval`/`exec`, weak hashes, hard-coded credentials, insecure temp files,
unverified TLS, unsafe deserialisation). It ships in the dev extra, outside runtime dependencies.
Nothing is suppressed inline (a test refuses `# noqa: Sxxx` in `src`).

One policy exception is handled by test, not suppression: `S101` (`assert`). All 27 `assert`s in
`src` are `x is not None` or enum narrowing; none guards authority, validates input or enforces a
limit. `tests/security/test_sast_policy.py` pins that form (anything else must be an explicit
`raise`), forbids `assert` in security-critical modules, and adds precise AST backstops for dynamic
execution, unsafe deserialisation, disabled TLS verification and weak hashes, plus a scan of all
Python source for invisible and bidirectional control characters ("Trojan Source"). That scan found a
real instance: a test literal written as three zero-width characters, now spelled with escapes.

**False positives.** Fix the code when it is a finding; if it is a false positive, argue it in a
test that fails when the reasoning stops being true. TypeScript has no SAST beyond `tsc --noEmit`
(`npm run lint` type-checks; it is not ESLint) and a dependency audit: the dashboard is a thin
client of the authenticated API. That is a stated limitation.

## 5. Secret scanning

gitleaks over the **full git history** and the **working tree**, configured by `.gitleaks.toml`
(default ruleset fully on). Two allowances only: one reviewed false positive - the *token count*
budget-check argument list (a token count and a cost estimate passed as keyword arguments) in `llm/accounting.py`,
allowed by rule (`generic-api-key`) **and** path **and** anchored matched text together - and
git-ignored tool directories. Verified with the real scanner: `regexTarget = "line"` would have hidden
a genuine secret appended to the allowed line; `"match"` does not, and a test plants both shapes.

## 6. Container scanning

Phase 14 builds the backend and frontend production images and scans the exact local artifacts with
Trivy 0.67.2 before publication. `scripts/security_gate.py --strict --require-container-scan
--container-image ...` rejects missing/mutable release identity, a missing scanner, non-JSON output,
an absent image ID, an empty target list, or any HIGH/CRITICAL vulnerability. Findings block whether
or not a fix is currently available. Temporary acceptance requires an explicit, reviewed,
expiry-bearing policy change; there is no silent ignore file. Scanner-database unavailability fails
closed.

Trivy emits CycloneDX SBOMs from each final image. `scripts/validate_sbom.py` requires non-empty
components, known final-stage packages and the actual final image ID, preventing an empty or wrong-image
SBOM from satisfying the gate. Trusted releases retain SBOMs as artifacts and create GitHub OIDC provenance attestations
for GHCR digests. PR images are neither published nor trusted-signature candidates.

## 7. The gate

`python scripts/security_gate.py [--strict] [--offline] [--require-container-scan] [--json PATH]`

Checks: live-schema tenancy/privilege audit, the `security` marker test suite, SAST, dependency-lock
policy, runtime-dependency declaration, repository hygiene, `pip-audit`, `npm audit`, gitleaks history
and tree, container scan. Exit 0 = pass, 1 = failure, 2 = error. **Fail closed:** a missing scanner, a
timeout, a crash or a scanner that exits 0 without a clean report is a failure. `--strict` (what CI
must use) turns every skip into a failure. A pinned local `pip-audit` is used via `ASIC_PIP_AUDIT`.

## 8. Not covered

Automated dependency-update PRs, a selected cloud registry/cluster identity, and independent
third-party signer trust are not configured. The release/deploy workflows verify this repository's
release provenance. Signing is exercised by GitHub
only on a trusted tag/manual run; local work does not claim a trusted signature. Production image,
Trivy, gitleaks, Terraform, PostgreSQL and kind-node images are digest-pinned. Existing observability
tools are also digest-pinned: Prometheus 3.14.0 and Collector Contrib 0.161.0 in
`scripts/check_observability.sh`. Gitleaks is pinned to 8.30.1, retaining support for the reviewed
rule-specific allowances. Kind and actionlint binary downloads require exact SHA-256 checksums.
