# ADR-0012: Native PostgreSQL ENUM types for closed vocabularies

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** Project owner (Phase 3 approved implementation)
- **Spec reference:** §12, §15, §20
- **Supersedes / Superseded by:** none

## Context

The architecture package requires several *closed* vocabularies: incident event types
("adding a type is a schema change"), incident status, risk tiers, provenance labels,
policy verdicts. Phase 3 had to choose how these are represented in PostgreSQL.

The forces are unequal. Some of these vocabularies are ordinary application state
(`chunk_strategy`); others are safety-relevant (`risk_tier`, `provenance_label`), where an
unrecognised value written by a buggy or compromised writer would defeat a constraint that
depends on it — `risk_tier <> 'r3'` cannot protect against a tier the database will happily
accept as free text.

## Decision

**Use native PostgreSQL `ENUM` types for all 38 domain vocabularies**, generated from
Python `StrEnum` classes, storing member *values* rather than names.

## Alternatives considered

### Option A — Native `ENUM` types (chosen)

- **Pros:** The database refuses an unknown value rather than trusting every writer.
  Adding a member requires a migration, which is exactly the change control §12 asks for.
  Check constraints that reference specific values (`risk_tier <> 'r3'`) become meaningful.
  Self-documenting in `psql`. Compact storage.
- **Cons:** `ALTER TYPE ... ADD VALUE` cannot run inside a transaction in older versions
  (fine on 16, but a constraint to remember). **Removing** a value is genuinely awkward.
  Autogenerated `op.drop_table` does not drop the type, which broke our first downgrade.
- **Cost to adopt:** Low, plus the downgrade fix described below.

### Option B — `VARCHAR` + `CHECK` constraint (rejected)

- **Pros:** Trivial to add and remove values. No type-drop problem. Simpler migrations.
- **Cons:** The check constraint has to be rewritten on every change, and a check
  constraint is easy to add *without* — a nullable free-text column carrying a status is
  the common failure. Larger storage. No introspectable vocabulary.
- **Cost to adopt:** Low.

### Option C — Lookup tables with foreign keys (rejected)

- **Pros:** Values are data; adding one needs no DDL; supports display metadata.
- **Cons:** Turns every status read into a join. Makes a vocabulary *open* by
  construction, which is the opposite of the requirement. Rows can be deleted.
- **Cost to adopt:** Moderate, and permanently more complex to query.

## Rationale

The decisive factor is that **several of these vocabularies are load-bearing for safety**.
`risk_tier` participates in `CHECK (risk_tier <> 'r3')`, which is how "destructive actions
are not expressible" (SI-5) is enforced. `provenance_label` participates in
`CHECK (category <> 'external' OR provenance NOT IN ('system','human'))`, which is how
"external content is never authoritative" (SEC-I4) is enforced. Both constraints assume the
column can only hold known values; a `VARCHAR` column makes that assumption false.

Option C was rejected for the same reason from the other direction: it makes the vocabulary
open, and an open vocabulary cannot be a closed one.

The awkwardness of *removing* an enum value is real but rare and correct: removing a status
from a system with historical rows carrying it is a data migration whether or not the type
system makes it obvious.

## Consequences

- **Positive:** Unknown values are rejected at the database. Safety check constraints are
  meaningful. Vocabulary changes are visible in migration review.
- **Negative / accepted trade-offs:** Value removal requires a type rewrite. Enum types
  must be dropped explicitly on downgrade — see below.
- **Security and permissions:** Positive; two safety invariants depend on it.
- **Observability and evaluation:** Neutral.
- **Failure modes and recovery:** One real defect surfaced and was fixed — Alembic's
  autogenerated `downgrade` drops tables but **not** the ENUM types they used, so
  `downgrade` followed by `upgrade` failed with `type "risk_tier" already exists`. The 0002
  migration now derives the type list from the models and drops each on downgrade, and
  `TestEnumTypeParity` asserts the database and the models agree.
- **Operational and cost impact:** Negligible.

## Reversal cost and revisit trigger

**Reversal cost: moderate.** Converting to `VARCHAR` + `CHECK` is a mechanical migration
per column, but there are 38 types across 36 tables.

Revisit if: a vocabulary needs to be tenant-extensible (which would mean it was never
closed, and belongs in a lookup table); or if enum value churn during development becomes
a recurring migration burden — measured as more than a handful of value removals.
